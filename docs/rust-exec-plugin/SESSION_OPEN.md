> 用户问题：会话打开过慢，有没有办法通过这个插件解决？
> 结论先说：**能，但先要分清慢在哪一段**。实测后端（读盘→解码→解析→投影）在最大会话上只占 ~115 ms，
> 秒级等待不在这一段；插件真正的杠杆是**投影服务（P3）+ 首屏切片**，而不是"用 Rust 重写解码"。

## 1. 实测数据（2026-10-19，8 个真实会话日志）

| 会话（截断） | 压缩 | 解压 | zstd 帧数 | 记录数 | 解码 | Node 解析 | 投影 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| session-b42bdabf | 2,093 KB | 7,346 KB | 1,254 | 2,046 | 30.8 ms | 41.4 ms | 0.9 ms |
| e828d9a4 | 749 KB | 2,966 KB | 464 | 734 | 20.2 ms | 18.5 ms | 1.9 ms |
| session-e4f968d8 | 795 KB | 2,733 KB | 563 | 925 | 22.1 ms | 20.2 ms | 0.6 ms |
| 131127bf | 532 KB | 2,219 KB | 350 | 563 | 20.0 ms | 19.4 ms | 0.6 ms |

- zstd 解码速率 97–233 MB/s（`node:zlib`，单流串行）；Node `JSON.parse` 7 MB ≈ 41 ms；投影配对 ≈ 1 ms。
- **最大会话后端合计 ≈ 115 ms**（解码 31 + 读取 42 + 解析 41 + 投影 0.9）。
- 渲染面：该会话 269 条消息 / 903 个内容块 / 1.0 MB 文本 / 13 个代码块；
  DSH 客户端**已用 `@tanstack/react-virtual` 虚拟化**（`dsh-client-ui-chat/lib/client.js:290`），代码高亮走 shiki（仅可见块）。

## 2. 结论：慢不在解码，在"打开编排 + 客户端水合"

后端能被 Rust 直接加速的部分上限 ≈ 115 ms/7.3 MB，即使做到 0 也只省一成秒。
用户体感的"秒级"更可能来自：

1. **宿主打开编排**：锁检查 → 日志尾部重放（token meter 的 `fold` 也是 O(事件数)）→ 投影重建 → attachments/workspace 变更 →
   逐段串行，且可能在缓存未命中时全量重算；
2. **客户端水合**：虚拟化只减少 DOM，但首帧仍要拿到完整 turn 列表与块骨架，markdown 解析 + shiki 初始化（wasm/语法加载）是固定成本；
3. **首屏块数**：900 块骨架里只要一次渲染 100+ 个 markdown 块，就足以到几百 ms 到秒级。

所以正确的做法是**先埋点定位，再按段优化**，不要重复"优化了不是瓶颈的地方"（P1 之前踩过一次：工具时间占 71%，但 Rust 能回收的只有其中一部分）。

## 3. 插件能做的三层（按收益排序）

### L1 帧索引 + 多帧并行解码（对超大/长历史会话）

zstd 日志是**逐帧追加**的（7.3 MB = 1,254 帧，平均 5.8 KB/帧，帧间独立）。Rust 可以：

- 建 `<sid>.idx`：`[{frameOff, compressedLen, seqFrom, seqTo, byteOff}]`，与日志同目录、原子写；
- 打开时**只解尾部帧**（首屏只需要最后 K 轮）；
- **多帧并行解码**：1,254 个独立帧分给 8 线程 → 相对单流 ≈5–8×（`node:zlib` 无此能力）。

收益：仅对 >20 MB 或 >1 万记录的历史会话明显（当前最大 7.3 MB，省 ~25 ms）。**不是当前的解药**，但为"长期使用后会话越来越大"兜底。

### L2 投影服务（P3，真正的主菜）

把"打开会话"从**计算**变成**读取**：

- 增量维护视图模型：`turns[]`（每轮：起止 seq、块摘要、token 估算、tool 调用配对、是否含错误）；
- 追加事件时同步更新（O(Δ)），落盘为紧凑快照（当前 DSH 的 `session_projcache` 已有类似物，17–25 KB/会话，说明这条路 DSH 自己也在走）；
- 打开时一次 `mmap` 读快照 + 尾部增量 → 后端成本降到 ~5 ms 量级；
- 关键是**语义不变**：真相源仍是 DSH 的 append-only 日志，投影可丢弃可重建，不接管写路径（风险最低的旁路方案）。

### L3 首屏切片协议（配合客户端）

- `session.open(sid, {limit: 30, cursor})` → 返回**尾部 30 轮** + `hasMore/cursor/totalTurns`；
- 客户端先渲染这 30 轮（~50–80 块），向上滚动时按 cursor 增量拉更早的块；
- 配合已有 react-virtual，首屏 hydrate 量从 900 块降到 ~60 块，这是把"秒级"变"百毫秒级"的唯一直接手段；
- 需要客户端侧配合：优先走 **P4 自定义面板/渲染接管**（风险中），或先做一个"插件会话视图"入口，不动默认聊天渲染。

## 4. 先埋点（18:00 恢复后第一步，30 分钟）

在宿主插件里加一个只读计时中间件 + 客户端 `performance.mark`，记录 4 段：

| 段 | 打点位置 | 期望（目标） |
| --- | --- | --- |
| T1 读盘+解锁 | host：打开入口 → 读到首帧 | ≤ 10 ms |
| T2 解码+解析 | host：zstd 解全部帧 → 记录数组 | ≤ 50 ms（7.3 MB） |
| T3 投影+token fold | host：数组 → 视图模型 | ≤ 20 ms |
| T4 客户端水合 | client：收到 → 首帧 committed | **当前未知，重点观测** |

验收目标（7.3 MB / 2,046 记录会话）：首屏 ≤ 150 ms、全量 ≤ 400 ms；若 T4 超 500 ms，则 L2+L3 的优先级高于 L1。

## 5. 不做的事

- **不替换 DSH 的会话真相源**：`session-persistence` 虽是可替换 seam（README 明确允许第三方 backend），但接管写入会牵动锁、
  版本、迁移，收益与风险不匹配；先做只读投影旁路，收益验证后再谈。
- **不用 Rust 重写 markdown/shiki**：渲染成本在浏览器，搬到 Rust 只会多一次序列化。
